# 第 5 部分：运维与故障排除


## 1. 健康检查

每个服务都必须暴露健康检查端点。

### 应用健康检查端点

```typescript
// 示例：Node.js / Express
import { Router } from 'express';

const router = Router();

// 存活探针：进程是否正在运行？
router.get('/health', (req, res) => {
  res.json({
    status: 'ok',
    timestamp: new Date().toISOString(),
    uptime: process.uptime(),
    environment: process.env.APP_ENV,
  });
});

// 就绪探针：服务是否能处理请求？
router.get('/health/ready', async (req, res) => {
  try {
    await database.query('SELECT 1');
    await cache.ping();
    res.json({ ready: true });
  } catch (error) {
    res.status(503).json({ ready: false, error: error.message });
  }
});
```

### Compose 健康检查配置

```yaml
services:
  api:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 30s     # 启动宽限期
```

### 检查健康状态

```bash
# 从宿主机
curl -s http://localhost:3000/health | jq .

# 从另一个容器
docker compose exec frontend curl -s http://api:3000/health

# 查看 Compose 状态
docker compose ps
```

## 2. 日志记录

### 日志驱动配置

```yaml
# compose.prod.yaml
services:
  api:
    logging:
      driver: "json-file"
      options:
        max-size: "10m"        # 达到 10MB 时轮转
        max-file: "3"          # 保留 3 个轮转文件
        labels: "service=api,environment=prod"
```

### 查看日志

```bash
# 实时跟踪所有日志
docker compose logs -f

# 实时跟踪特定服务
docker compose logs -f api

# 最近 100 行
docker compose logs --tail=100 worker

# 搜索错误
docker compose logs | grep -i error

# 从特定时间开始
docker compose logs --since "2026-03-19T10:00:00" api
```

### 应用层日志记录

生产环境使用结构化日志（JSON）便于解析：

```javascript
// 示例：结构化日志记录器
logger.info({
  event: 'request_completed',
  method: 'GET',
  path: '/api/users',
  statusCode: 200,
  duration_ms: 45,
  requestId: 'abc-123'
});
```

## 3. 指标与追踪

### Prometheus 指标（示例）

```typescript
import prom from 'prom-client';

const httpDuration = new prom.Histogram({
  name: 'http_request_duration_seconds',
  help: 'Duration of HTTP requests in seconds',
  labelNames: ['method', 'route', 'status_code'],
});

const databaseQueryDuration = new prom.Histogram({
  name: 'database_query_duration_seconds',
  help: 'Duration of database queries',
  labelNames: ['query_type'],
});

const activeConnections = new prom.Gauge({
  name: 'active_connections',
  help: 'Number of active connections',
});
```

### 分布式追踪（使用 OpenTelemetry 示例）

```typescript
import { trace } from '@opentelemetry/api';

const tracer = trace.getTracer('app-tracer');

async function handleRequest(req) {
  const span = tracer.startSpan('handle_request');
  try {
    // ... 业务逻辑
    span.setAttribute('http.method', req.method);
    span.setAttribute('http.route', req.path);
  } finally {
    span.end();
  }
}
```

## 4. 回滚流程

### 立即服务回滚

如果生产部署出现问题，快速回滚到上一个镜像：

```bash
#!/bin/bash
set -euo pipefail

PREVIOUS_TAG="prod-xyz9876"     # 从部署日志获取

echo "正在回滚到 $PREVIOUS_TAG"

docker pull registry.company.com/api:${PREVIOUS_TAG}

docker compose \
  --env-file ./env/compose.prod.env \
  -f compose.yaml \
  -f compose.prod.yaml \
  up -d --force-recreate api

# 验证
sleep 10
curl -s https://api.company.com/health

echo "回滚完成"
```

### 数据库回滚

```bash
# 如果迁移导致问题：

# 1. 从迁移前备份恢复
./scripts/restore-db.sh ./backups/db_prod_20260318_100000.sql.gz

# 2. 使用上一版本代码重启服务
docker compose restart api
```

### 时间点恢复

```bash
# 查找事故前最新的备份
BACKUP_FILE=$(find ./backups -name "db_prod_*.sql.gz" | sort -r | head -1)
./scripts/restore-db.sh "$BACKUP_FILE"
```

## 5. 故障排除：Docker Compose

### "端口已被占用"

**原因**：另一个进程正在使用该端口。

```bash
# 查找占用端口的进程
lsof -i :3000          # macOS/Linux
netstat -ano | findstr :3000   # Windows

# 停止容器
docker compose down

# 或终止占用该端口的特定容器
docker kill $(docker ps -q --filter "publish=3000")

# 重启
docker compose up -d
```

### "服务无法连接数据库"

**原因**：数据库尚未就绪，或不在同一网络中。

```bash
# 检查数据库状态
docker compose ps database

# 检查健康状态
docker compose exec database pg_isready -U devuser -d platform_db

# 查看日志
docker compose logs database

# 如果不健康则重启
docker compose restart database
```

### "无法解析主机名"

**原因**：容器内 DNS 解析失败。

```bash
# 快速修复：重启
docker compose restart

# 持久修复：在 compose.yaml 中添加 DNS
# services:
#   api:
#     dns: [8.8.8.8, 1.1.1.1]

docker compose up -d --force-recreate api
```

## 6. 故障排除：开发容器

### 开发容器启动时间过长

**原因**：首次构建 Docker 镜像（下载基础镜像、安装依赖）、Docker Desktop 缓慢，或网络缓慢。

**解决方案**：

```bash
# 在打开之前预构建镜像
cd platform-dev
docker compose build gateway

# 或使用预构建镜像而不是从 Dockerfile 构建
# 在 devcontainer.json 中，使用 "image" 而不是 "dockerComposeFile"：
{
  "image": "node:20-alpine",
  "postCreateCommand": "npm install"
}
# 这以启动速度换取自定义能力
```

### "无法启动开发容器"

**原因**：Compose 语法错误、服务缺失，或资源限制。

```bash
# 验证 Compose 文件
docker compose \
  --env-file ./env/compose.dev.env \
  -f compose.yaml \
  -f compose.dev.yaml \
  config > /tmp/merged.yaml

# 查看合并后的配置
cat /tmp/merged.yaml

# 检查 Docker Desktop 资源分配
# 至少分配：4 个 CPU、6GB 内存、20GB 磁盘

# 查看日志
docker compose logs api

# 重建容器
docker compose build --no-cache api
docker compose up -d api
```

### "VS Code 无法连接容器"

**原因**：容器崩溃或扩展问题。

```bash
# 检查容器是否正在运行
docker compose ps api

# 如果已退出，查看原因
docker compose logs api

# 重启
docker compose restart api

# 在 VS Code 中：命令面板 → "Dev Containers: 在容器中重新打开"

# 如果仍然失败，则重建
docker compose build --no-cache api
docker compose up -d api
```

### SSH 代理未转发到容器内

**原因**：SSH 套接字未挂载到容器中。

**解决方案**：在 `devcontainer.json` 中添加：

```json
{
  "mounts": [
    "source=${localEnv:SSH_AUTH_SOCK},target=/run/host-services/ssh-auth.sock,readonly"
  ]
}
```

并在 compose.yaml 服务中添加：

```yaml
services:
  gateway:
    environment:
      SSH_AUTH_SOCK: /run/host-services/ssh-auth.sock
```

### macOS 上绑定挂载性能缓慢

**原因**：macOS Docker Desktop 使用虚拟化层，文件同步较慢。

**解决方案**（按优先级排序）：

1. **为 node_modules 使用命名卷：**
```yaml
services:
  gateway:
    volumes:
      - ../api-gateway:/workspace/api-gateway
      - node_modules:/workspace/api-gateway/node_modules  # 独立卷，速度更快
volumes:
  node_modules:
```

2. **启用 VirtioFS**（macOS 上更快的文件同步）：
   - Docker Desktop → 设置 → 资源 → 勾选 "使用 VirtioFS"
   - 需要 Docker Desktop 4.22+

3. **接受缓慢** — 慢 30-40% 是典型的，对大多数工作流来说不是致命的。

### 多个开发容器冲突同一服务

**问题**：两个 VS Code 窗口争夺同一个 gateway 服务。

**解决方案**：为不同服务使用单独的 VS Code 窗口。如果需要在同一服务上打开两个窗口，请使用不同的 Docker Compose profile 或单独的 compose 文件。

### 修改 .env 后环境变量未重新加载

**原因**：Docker Compose 在启动时解析 `env_file`；修改后需要完全重启。

**解决方案**：

```bash
# 停止并移除容器（强制重新构建环境）
docker compose down gateway
docker compose up -d gateway

# 然后在 VS Code 中重新连接
```

## 7. 故障排除：文件权限

### 挂载卷上的 "权限被拒绝"

**原因**：容器用户无法写入宿主机目录。

```bash
# 在宿主机上修复权限
chmod -R a+rw ~/workspace/api-gateway

# 或确保以下设置：
# devcontainer.json: "updateRemoteUserUID": true
# compose.yaml: user: vscode

# 重启
docker compose down api && docker compose up -d api
```

### "node_modules 无法从宿主机访问"

**这是预期且有意的设计。** 匿名卷用于防止性能问题：

```yaml
volumes:
  - ../api-gateway:/workspace/api-gateway
  - /workspace/api-gateway/node_modules    # 匿名卷（不在宿主机上）
```

重新安装依赖：

```bash
docker compose exec api npm ci
```

## 8. 故障排除：网络

### "服务之间无法通信"

```bash
# 验证两个服务都在运行
docker compose ps api ai-service

# 测试连接
docker compose exec api ping ai-service

# 验证是否在同一网络
docker network inspect <project>_default | grep -A 10 Containers
```

### "无法从容器访问数据库"

```bash
# 检查数据库是否在运行
docker compose ps database

# 查看日志
docker compose logs database | tail -20

# 尝试直接连接
docker compose exec api psql -h database -U devuser -d platform_db -c "SELECT 1"

# 如果连接被拒绝，请等待（数据库可能仍在启动）
sleep 10
docker compose exec api psql -h database -U devuser -d platform_db -c "SELECT 1"
```

## 9. 生产环境检查清单

### 基础设施

- [ ] 数据库有自动备份（至少每小时一次）
- [ ] 所有服务都配置了健康检查
- [ ] 资源限制设置适当
- [ ] 负载均衡器/入口配置了 SSL
- [ ] DNS 指向正确的端点

### 密钥管理

- [ ] 所有敏感值存储在密钥管理器中（不在 .env 文件中）
- [ ] 数据库密码在 90 天内轮换
- [ ] API 密钥有较短的有效期，尽可能配置自动轮换
- [ ] TLS 证书有效且配置了自动续期

### 监控与告警

- [ ] 应用指标已导出（Prometheus 格式或等效格式）
- [ ] 日志已集中化且可搜索
- [ ] 配置了告警：高 CPU、高内存、健康检查失败、错误率飙升
- [ ] 建立了值班轮换制度

### 测试

- [ ] 预发环境部署已通过负载测试验证
- [ ] 回滚流程已手动测试
- [ ] 数据库备份/恢复已测试
- [ ] 所有服务通过冒烟测试

### 文档

- [ ] 部署操作手册已编写并测试
- [ ] 事件响应流程已记录
- [ ] 架构图保持最新
- [ ] 团队了解部署脚本的位置
