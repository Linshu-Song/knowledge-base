# 仓库架构概述

多服务平台存在两种主要的仓库策略。没有哪种是绝对优越的；正确的选择取决于团队规模、发布节奏和组织架构。

### 单体仓库 vs 多仓库

| 维度 | 单体仓库 | 多仓库 |
|------|----------|--------|
| **代码共享** | 优秀。应用间原生导入。 | 复杂。需要发布到私有仓库或使用 Git 子模块。 |
| **原子性变更** | 是。单个 PR 可以同时修改 API、后端和前端。 | 否。需要多个 PR 并协调。 |
| **新成员入职** | 简单。`git clone` 一次。 | 中等。需要克隆多个仓库。 |
| **CI/CD 复杂度** | 高。需要路径过滤 + 构建工具。 | 低。标准的单仓库流水线。 |
| **访问控制** | 全有或全无。 | 按仓库精细化控制。 |

### 单体仓库

所有服务位于**一个 Git 仓库**中。

**优势：**
- 跨服务原子性变更
- 通过本地引用共享代码——无需发布到包仓库
- 统一的 CI/CD，支持基于路径的过滤
- 当共享接口变更时，IDE 会立即在所有消费者中暴露错误

**权衡：**
- 仓库随时间增长变大
- 需要工具支持（Nx、Turborepo、Bazel）应对复杂度增长

### 多仓库

每个服务有**独立仓库**。中心平台仓库管理共享基础设施。

**优势：**
- 每个服务独立的 CI/CD、版本控制和发布节奏
- 清晰的团队所有权边界
- 天然边界强制——不会意外耦合服务

**权衡：**
- 跨服务变更需要协调多个 PR
- 共享代码必须发布到仓库或 vendoring

### 决策指南

| 因素 | 单体仓库 | 多仓库 |
|------|----------|--------|
| 团队规模 | 小型至中型（< 30 人） | 中型至大型 |
| 发布节奏 | 协调发布 | 每个服务独立 |
| 共享代码 | 大量跨服务共享 | 最小化共享，优先 API 契约 |
| 所有权 | 可能模糊 | 按仓库清晰划分 |

**选择单体仓库如果：** 团队跨技术栈高度协作，或饱受"版本地狱"困扰。

**选择多仓库如果：** 团队严格专业化，或某仓库非常庞大（大型模型、重型二进制）。
