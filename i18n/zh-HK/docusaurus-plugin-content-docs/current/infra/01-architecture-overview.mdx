# 儲存庫架構概述

多服務平台存在兩種主要的儲存庫策略。兩者沒有絕對的優劣之分；正確的選擇取決於團隊規模、發布節奏和組織結構。

### 單一儲存庫 vs 多元儲存庫

| 維度 | 單一儲存庫 | 多元儲存庫 |
|------|-----------|------------|
| **程式碼共享** | 極佳。可跨應用程式原生導入。 | 複雜。需要發布到私人註冊表或使用 Git 子模組。 |
| **原子性變更** | 是。單一 PR 即可變更 API、後端和前端。 | 否。需要多個 PR 並協調。 |
| **新成員入職** | 簡單。`git clone` 一次。 | 中等。需要克隆多個儲存庫。 |
| **CI/CD 複雜度** | 高。需要路徑篩選 + 建構工具。 | 低。標準的單儲存庫管線。 |
| **存取控制** | 全有或全無。 | 按儲存庫精細控制。 |

### 單一儲存庫

所有服務位於**單一 Git 儲存庫**中。

**優點：**
- 跨服務的原子性變更
- 透過本地引用共享程式碼——無需發布到套件註冊表
- 使用基於路徑篩選的統一 CI/CD 管線
- 當共享介面變更時，IDE 會在所有消費者中顯示錯誤

**取捨：**
- 儲存庫會隨時間增長而變大
- 需要工具支援（Nx、Turborepo、Bazel）應對複雜度增長

### 多元儲存庫

每個服務有**獨立儲存庫**。中央平台儲存庫管理共享基礎架構。

**優點：**
- 每個服務獨立的 CI/CD、版本控制和發布節奏
- 清晰的團隊所有權邊界
- 自然邊界執行——不會意外耦合服務

**取捨：**
- 跨服務變更需要協調多個 PR
- 共享程式碼必須發布到註冊表或 Vendored

### 決策指南

| 因素 | 單一儲存庫 | 多元儲存庫 |
|------|-----------|------------|
| 團隊規模 | 小型至中型（< 30 人） | 中型至大型 |
| 發布節奏 | 協調發布 | 每個服務獨立 |
| 共享程式碼 | 重度跨服務共享 | 最少共享，偏好 API 合約 |
| 所有權 | 可能模糊 | 按儲存庫清晰劃分 |

**選擇單一儲存庫如果：** 團隊跨技術棧高度協作，或飽受「版本地獄」困擾。

**選擇多元儲存庫如果：** 團隊嚴格分工，或某儲存庫非常龐大（大型模型、重型二進位檔）。
