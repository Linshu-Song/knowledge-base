## 1. 單一儲存庫與多元儲存庫

多服務平台存在兩種主要的儲存庫策略。兩者沒有絕對的優劣之分；正確的選擇取決於團隊規模、發布節奏和組織結構。

### 各項功能比較

| 維度 | 單一儲存庫 | 多元儲存庫 |
|-----------|----------|----------|
| **程式碼共享** | 極佳。可跨應用程式原生導入。共享函式庫可直接被前端和 API 使用。 | 複雜。需要發布到私人套件註冊表或使用 Git 子模組。 |
| **原子性變更** | 是。單一 PR 即可變更 API 合約、後端實作和前端消費者。 | 否。需要跨多個儲存庫建立多個 PR 並仔細協調。 |
| **新成員入職** | 簡單。`git clone` 一次。所有程式碼、infra 和文件立即可用。 | 中等。需要克隆平台儲存庫加上多個服務儲存庫。 |
| **CI/CD 複雜度** | 高。管線必須使用路徑篩選或 Nx/Turborepo 等工具。 | 低。標準管線——如果某個儲存庫被推送，就建構並部署該儲存庫。 |
| **Git Clone 大小** | 較大。包含所有服務的全部歷史記錄。 | 較小。開發者只提取他們相關的部分。 |
| **語言混合** | 中等。混合生態系統（例如不同的依賴管理器）需要紀律。 | 簡單。每個儲存庫完全專用於自己的語言生態系統。 |
| **存取控制** | 全有或全無。通常每個人都有整個程式碼庫的讀取權限。 | 精細。可以輕鬆限制對特定服務的存取。 |

### 單一儲存庫

所有服務、應用程式和共享函式庫都存在於**單一 Git 儲存庫**中。

**優點：**
- 跨服務的原子性變更（一次提交同時觸及 API 和前端）
- 透過本地引用共享程式碼——無需發布到套件註冊表
- 使用基於路徑篩選的統一 CI/CD 管線
- 單一克隆，單一分支策略
- 當共享介面變更時，IDE 和編譯器會在所有消費者中顯示錯誤

**取捨：**
- 儲存庫會隨著時間增長而變大
- CI 必須使用路徑篩選以避免重建所有內容
- 隨著複雜度增長需要工具支援（例如 Nx、Turborepo、Bazel）
- 如果團隊規模大，所有權邊界會模糊

### 多元儲存庫

每個服務都有自己**獨立的 Git 儲存庫**。一個中央「平台」儲存庫管理共享基礎架構（Compose 檔案、Dev Container、開發環境配置）。

**優點：**
- 每個服務獨立擁有 CI/CD、版本控制和發布節奏
- 清晰的團隊所有權邊界
- 更小、更專注的儲存庫
- 無需單一儲存庫工具支援
- 自然邊界執行——開發者不會意外耦合服務

**取捨：**
- 跨服務變更需要協調多個 PR
- 共享程式碼必須發布到註冊表（npm、PyPI 等）或 Vendored
- 新成員入職需要克隆多個儲存庫
- 保持基礎架構配置同步需要手動操作（由中央平台儲存庫緩解）

---

### 深度探討：單一儲存庫的優勢

#### 「共享合約」模式

在多服務平台中，後端 API、前端和後台工作者通常共享**資料傳輸物件（DTO）**、驗證結構定義和事件負載。

**在多元儲存庫中**，向訊息負載添加新欄位：
1. 更新 shared-contracts 儲存庫 → 發布新版本
2. 更新 API 閘道儲存庫 → 安裝新版本 → 部署
3. 更新工作者儲存庫 → 安裝新版本 → 部署

**在單一儲存庫中**：
1. 在**同一分支**中更新共享合約檔案、更新閘道和工作者的程式碼
2. 執行測試。合併一個 PR。兩個服務一起部署。

#### 重構信心

當你在單一儲存庫中變更核心工具函式或 API 介面時，你的 IDE 和編譯器會立即在**每個**使用它的應用程式中顯示錯誤。在多元儲存庫中，你可能直到下游儲存庫的 CI 執行後數小時或數天才發現這個破壞性變更。

---

### 深度探討：多元儲存庫的優勢

#### 邊界執行

多元儲存庫自然防止「義大利麵條式程式碼」。在單一儲存庫中，開發者可能直接從一個服務導入資料庫模型到另一個服務。多元儲存庫使這變得不可能，強制透過實際的網絡邊界（API、訊息佇列等）進行通訊。

#### 建構隔離

如果某個團隊維護著使用完全不同工具鏈的資源密集型建構，他們不需要瀏覽不相關的配置。他們的 CI/CD 管線保持專注且獨立。

## 2. 單一儲存庫核心概念

### 工作區

大多數語言生態系統都支援工作區連結：

```
# Node.js (npm/yarn/pnpm)
"workspaces": ["apps/*", "libs/*"]

# Python (poetry/uv)
# 在 pyproject.toml 中使用路徑依賴

# Go
# 使用帶有 replace 指令的 Go modules
```

### 基於路徑的 CI/CD

僅重建和重新部署受變更影響的服務：

```yaml
# 範例：僅當特定路徑變更時觸發部署
on:
  push:
    paths:
      - 'apps/api-gateway/**'
      - 'libs/shared-types/**'   # 共享依賴變更觸發重建
```

### 建構工具

隨著單一儲存庫的增長，依賴感知建構工具變得必不可少：

- **Turborepo** / **Nx**：計算依賴圖，只建構變更的部分
- **Bazel** / **Pants**：適用於大規模系統的語言無關、密封式建構

```bash
# Turborepo：僅建構自 'main' 以來受影響的服務
npx turbo run build --filter=...[origin/main]
```

## 3. 多元儲存庫核心概念

### 中央平台儲存庫

一個專用儲存庫（例如 `platform-dev`）持有所有共享基礎架構：

```
platform-dev/
├── compose.yaml               # 基本編排（資料庫、佇列、快取）
├── compose.dev.yaml           # 開發覆寫
├── compose.prod.yaml          # 生產覆寫
├── env/                       # 環境變數檔案
├── .devcontainer/             # 每個服務的 Dev Container 定義
├── docker/                    # 共享基礎 Dockerfiles
├── scripts/                   # 設定、部署、備份指令碼
└── docs/                      # 入職、架構文件
```

### 服務儲存庫

每個服務都是獨立的：

```
api-gateway/                   # 獨立 Git 儲存庫
├── Dockerfile                 # 繼承自 platform-dev 基礎映像
├── src/
├── tests/
└── package.json
```

### Git 憑證管理

Git 憑證（SSH 金鑰、權杖）保留在主機上。容器透過 SSH Agent 轉發重用這些憑證——私密金鑰不會進入容器。

## 4. 兩種模式的共享函式庫

### 在單一儲存庫中

本地套件透過工作區工具自動連結：

```
# 應用程式將本地函式庫作為普通依賴引用
{
  "dependencies": {
    "@company/shared-types": "*"    // 解析為 libs/shared-types
  }
}
```

在根目錄執行 `npm install` 會將函式庫符號連結到每個應用程式的 `node_modules`。

### 在多元儲存庫中

共享程式碼必須發布到註冊表、Vendored，或透過共享合約公開：

- **選項 A**：作為私人套件發布到 npm/PyPI
- **選項 B**：使用 Git 子模組（由於複雜性通常不建議）
- **選項 C**：定義 API 合約（OpenAPI、gRPC、GraphQL 結構定義）並為每個服務產生客戶端程式碼
- **選項 D**：從平台儲存庫透過同步指令碼複製共享類型/範本

│   │   └── package.json              # @company/web-app

│       └── requirements.txt

├── libs/
│   ├── shared-types/
│   │   ├── package.json              # @company/shared-types

## 6. 決策指南

| 因素 | 單一儲存庫 | 多元儲存庫 |
|--------|----------|----------|
| 團隊規模 | 小型至中型（< 30 位開發者）| 中型至大型 |
| 發布節奏 | 協調發布 | 每個服務獨立 |
| 共享程式碼 | 重度跨服務共享 | 最少共享，偏好 API 合約 |
| CI/CD 複雜度 | 需要路徑篩選 + 建構工具 | 每個儲存庫的管線較簡單 |
| 新成員入職 | 單一克隆 | 多個克隆 + 平台儲存庫 |
| 所有權 | 可能模糊 | 每個儲存庫清晰的所有權 |
| 語言多樣性 | 工作區工具支援良好 | 每個儲存庫選擇自己的技術棧 |
| 存取控制 | 全有或全無 | 每個儲存庫精細控制 |

### 選擇單一儲存庫，如果：
- 你的團隊在整個技術棧上高度協作（例如全端開發者在同一個 sprint 中觸及資料庫、API 和前端）
- 你飽受維護內部套件或共享依賴的「版本地獄」之苦
- 你依賴跨前端和後端的共享語言生態系統，並希望獲得端到端類型安全

### 選擇多元儲存庫（配合中央平台儲存庫），如果：
- 你的團隊嚴格分工（前端團隊從不觸及計算密集型服務程式碼）
- 你的某個儲存庫非常龐大（包含大型模型或重型二進位檔）會拖慢其他開發者的 Git 體驗
- 你想要最簡單的 CI/CD 管線，而不需要學習額外工具
- 你需要每個服務的精細存取控制

### 混合方法

將共享相同語言生態系統的服務分組到**單一儲存庫**中（例如前端 + API 閘道 + 工作者的組合），並將具有重型建構上下文且計算密集型的服務保持為獨立的**多元儲存庫**元件。無論你選擇哪種模式，基礎架構模式（Compose、Dev Container、環境管理）都保持相似。
